### Independent outcome verification findings (2026-09-01)

**Real bug found while building this, not hypothetical**: a bare `ToolCall` — an agent *requesting* something like `gh pr create`, before any result is known — was being scored as `CiOrDeploymentVerified @ 0.90` from the command string alone (`classify_command_string` accepted a `None` exit code as a high-confidence match). That's the exact "trusting intent as reality" failure this feature exists to catch, and it was live in the scoring path before this branch.

**Fix shape**: cross-checks each outcome claim against real state elsewhere in the trace — a `DoneClaimed` needs some real `ShellCommand` with `exit_code == Some(0)` somewhere in the session or its confidence drops to ≤0.10; a claim sourced from a bare `ToolCall` gets demoted in *kind*, not just confidence, from whatever rung it claimed down to `DoneClaimed` (confidence-only wouldn't have been enough — `compute_verifiability_score` branches on kind presence, not confidence); `ArtifactChanged` gets a real file/git check; `CommitObserved` gets a real `git cat-file` check against a parsed hash, falling back to a time-windowed `git log`. External CI/deploy claims are deliberately left unverified — no GitHub/Vercel API calls added, out of scope.

**Design call worth knowing about**: no schema changes. Adding a `verification` field to `OutcomeEvidence` would have touched 55+ struct-literal construction sites across all 20 adapters, for a fix scoped to one crate — so verification mutates `kind`/`confidence`/`summary` in place inside the existing detection path instead, meaning `Scanner::run_scan` and `TraceScorer::score` both pick it up automatically with no changes needed outside `crates/outcomes`.

233 passed workspace-wide (up from 211), zero regressions. Commit `386b23c` on `feat/outcome-independent-verification`, not pushed.

### OutcomeKind encoding fix findings (2026-09-01)

Confirmed the peer's diagnosis, with one correction: it's `crates/outcomes/src/outcome.rs`'s `outcome_kind_name()` at fault, not `routes.rs`. `routes.rs` had already been fixed earlier today (the NULL-defaulting + duplicate-key fix) to correctly expect PascalCase and map it forward to snake_case for the frontend — that fix was masking the real problem, not solving it. The real bug: `outcome_kind_name()` hand-lists PascalCase strings (`"CommitObserved"`, etc.), diverging from `OutcomeKind`'s own `#[serde(rename_all = "snake_case")]` derive in `crates/schema/src/event.rs`. The frontend's TypeScript `OutcomeKind` type (`apps/web/src/types/index.ts`) and every component that switches on it (`VerdictStamp.tsx`, `VerdictBoard.tsx`, `TracesExplorer.tsx`) are all snake_case — confirms snake_case is the right direction, not PascalCase.

**Root cause, precisely**: `Scanner::run_scan` (`crates/core/src/lib.rs`) writes `outcome_kind_name()`'s output straight into `sessions.primary_outcome`. Every session ever scanned has the wrong-case string sitting in the real database. A read-side fix alone (what `routes.rs` had) can't repair that — it just teaches every reader to work around bad data forever.

**Where PascalCase had leaked in, beyond the reported spots**:

| Location | What it did | Fix |
| --- | --- | --- |
| `crates/outcomes/src/outcome.rs` | Hand-listed PascalCase strings (the writer) | Now derives the string from `OutcomeKind`'s own serde encoding via `serde_json::to_value` — can't drift out of sync again |
| `crates/storage/src/lib.rs` `get_aggregate_stats` | SQL `IN (...)` list hardcoded PascalCase | Now snake_case, matching the fixed writer |
| `apps/cli/src/server/routes.rs` `outcome_distribution_key` | Mapped PascalCase → snake_case for the frontend | Now near-identity (input is already snake_case); kept the old PascalCase literals as a defense-in-depth fallback |
| `apps/cli/src/commands/blind_spots.rs`, `recall.rs`, `pr_blame.rs` | Each hand-rolled its own `confidence_for_outcome()` matching PascalCase, plus PascalCase fallback/comparison strings | All three flipped to snake_case — same bug class as the already-fixed `routes.rs` bug, independently reintroduced three more times |
| `apps/cli/src/main.rs` `agentworth traces --json` | Used `format!("{:?}", kind)` (Debug formatting → PascalCase) | Switched to `outcome_kind_name()` |

That's the "bitten twice" bug class landing a fifth and sixth time in the same session, across `blind_spots.rs`, `recall.rs`, `pr_blame.rs`, and the `traces --json` Debug-format spot — none of them shared code with each other or with `routes.rs`; each one independently re-derived the wrong casing by hand.

**Migration**: no schema-version table exists in this codebase (checked first, per the brief) — schema changes here follow a "check `PRAGMA table_info`, `ALTER TABLE` if missing" pattern. Added a data migration in the same spirit: an `UPDATE sessions SET primary_outcome = CASE ... END WHERE primary_outcome IN (the five old PascalCase literals)`, run unconditionally on every `Storage::initialize_schema()` call (i.e. every time a DB is opened). It's idempotent by construction — the `WHERE` clause can only ever match the old literals, so a second run touches zero rows. Tested against a file-backed fixture DB (`tempfile::NamedTempFile`, not `~/.agentworth/agentworth.db`): seeded rows in the old PascalCase encoding plus one already-snake_case row and one `NULL` row, re-ran `initialize_schema()` to simulate a real reopen, asserted every legacy row corrected and the other two untouched, then ran it a second time to confirm no further change.

**Is `verdict_breakdown.real_verified_rate > 1.0` the same root cause? No.** Traced `compute_verdict_breakdown` (`apps/cli/src/main.rs`) end to end: it never reads the stored `primary_outcome` string at all. It re-detects outcomes live from each trace and matches on the `OutcomeKind` enum directly, never through a string. It can't be touched by the casing bug.

Worked through the math on paper: `total_sessions` is an unfiltered `COUNT(*)`, and the loop's own session count is always `<=` that (same table, filtered down further, never up) — so `real_verified_tasks <= total_sessions` is a hard invariant of the current code, and a raw value like `1.09` most likely means "1.09%", not "109% — overcounted." That reading matches how this same codebase already treats this kind of field elsewhere: `calculate_cache_hit_ratio` (`crates/storage/src/lib.rs`) is also 0–100 scaled despite the `_ratio` name, and the CLI's own text view prints `verdict.real_verified_rate` straight into a `{:.1}%` format with no extra scaling — both confirm 0–100 is the intended scale here, so a small number isn't automatically an overflow.

That said, this function does have a real, separate, worth-fixing bug: it calls `list_sessions_filtered(&SessionFilter { limit: None, ... })` intending "no limit," but `list_sessions_filtered` treats an absent limit as **50**, not unlimited (`filter.limit.unwrap_or(50)`). On any index bigger than 50 non-stub sessions, the entire verdict breakdown silently reflects only the 50 most-recently-started sessions while being divided against the true full count — on a 10,188-session index that's about 0.5% real coverage, dressed up as if it covers everything. This makes the rate read *low*, never *high*, so it can't explain a >1.0 report either way — but it's a real bug in the exact "verified outcome counting" area, so flagging it separately (spawned as its own task) rather than folding it into this fix.

### The one real bug: mutex poisoning could wedge `agentworth serve` forever

`Storage` and `SqliteVectorStore` share one `Arc<Mutex<Connection>>`, locked with bare `.unwrap()` at 19 call sites across `crates/storage/src/lib.rs` and `crates/storage/src/vector/sqlite_store.rs`. `agentworth serve` runs a multi-threaded Axum server on this same shared `Storage` (`AppState { storage: Arc<Storage> }`, `tokio::runtime::Runtime::new()` — multi-thread by default). A panic inside any single request handler while the lock is held would poison the mutex permanently: every one of those 19 call sites then panics on every future call, turning one bad request into a permanent outage until someone restarts the process by hand.

Fixed: every `.lock().unwrap()` → `.lock().unwrap_or_else(PoisonError::into_inner)`. Safe because a `rusqlite::Connection` has no in-process invariant a panic mid-query could leave broken — SQLite already committed or rolled back at the engine level. Documented on both structs. Commit `c46e46d`.
